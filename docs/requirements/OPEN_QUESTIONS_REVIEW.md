Строки вариантов/блокеров ниже сохраняют первоначальный анализ; текущий статус всех 15 OQ и условные gates определяются [Release 1 decisions](RELEASE_1_DECISIONS.md#остатки-всех-15-oq). «Блокирует ТЗ» означает блокировку окончательного согласования соответствующего раздела, а не написания draft. «Блокирует архитектуру» означает невозможность окончательно выбрать соответствующие системные границы/решения; исследование вариантов возможно уже сейчас. Решение одного подпункта не закрывает составной OQ целиком.

## Порядок обсуждения

Сначала scope и masters (OQ-01–03), затем исключения/подтверждения и режимы работы (OQ-04, 06–08, 12), параллельно photo/device/NFR и каналы (OQ-05, 09–11). OQ-13 решается до общего barcode обмена; OQ-14 — до передачи исходного evidence; OQ-15 — до утверждения production acceptance. Это порядок согласования требований, не Development Roadmap.

Для фиксации ответа требуется: OQ и подпункт → точный вариант/граница → утверждающий → дата/источник → затронутые FR/NFR/UC → обновление статуса в реестре решений. Owner принял рекомендованную основу (PH2-001); конкретные ответы BD получены; составные OQ сохраняют только перечисленные в Release 1 decisions остатки.

## Блокирующие решения для System Architecture & Integrations

По DOC-001 открытые детали не блокируют передачу пакета ТЗ v1.0: команда уточняет их при реализации зависимого участка. Сводка текущих вопросов — [handoff](../DEVELOPMENT_HANDOFF.md#как-решать-вопросы-при-разработке).

**Текущий статус:** core architecture разблокирована; draft подготовлен. Signing/correction/active-route/vehicle recovery зависят от RQ-01–04, integration implementation — от INT-01–05, pilot acceptance — от BD-15/NFR. Следующий абзац — первоначальная оценка до согласования BD, не текущий перечень глобальных блокеров.

Безусловные для окончательного общего решения: **OQ-01–10 и OQ-12** в соответствующих частях. OQ-11 блокирует архитектуру подтверждённых communication channels до выбора production scope. OQ-13 блокирует общие с barcode-проектом компоненты только при включении их в scope. OQ-15 определяет параметры capacity/reliability и критерии запуска; OQ-14 — переносимость комплекта, но не архитектуру runtime.

Полные реализации и API не следует закреплять до согласования этих границ. Можно начинать контекстную схему и варианты с явными unresolved constraints. Сопоставление вопросов и пробелов: [Gap Analysis](REQUIREMENTS_GAP_ANALYSIS.md); функциональные требования: [ТЗ](TECHNICAL_SPECIFICATION.md).
