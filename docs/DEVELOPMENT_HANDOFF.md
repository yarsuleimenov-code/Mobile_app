# Mobile App Release 1 — передача разработчикам

**Пакет ТЗ v1.0 · 2026-10-16 · Подготовлен для передачи команде.** Пользователи пакета: разработчики mobile/backend/integrations, QA и Product. Прототип принят CEO; принятые UI/UX сохраняются. Эта версия фиксирует состав задания, а не приёмку production, окончательный выбор стека или утверждение нерешённых деталей.

## Что реализовать

Ядро первого релиза: приложение для iPhone/iPad, Home/Tasks/Scan/More, маршрут из Spoke API после Pre-trip, отдельные Pickup/Dropoff, грузовые места и измерения, фотографии, подтверждения сторон, подписи и PDF eBOL/POD, история версий, локальное сохранение и синхронизация. Зарегистрированный пользователь имеет полный доступ к данным и действиям приложения. Branch и физический склад — один бизнес-объект текущего scope.

Если данные груза невозможно предоставить, ответственный менеджер указывает, что отсутствует и почему; с этим комментарием можно продолжать. Жёсткого минимума фото нет. Это правило не отменяет подписи, достоверный контекст заказа и корректное сохранение. При ошибке/отказе передачи — сообщить диспетчеру и при необходимости перейти к следующей точке, не объявляя проблемную выполненной.

Создание/назначение маршрутов и Same Day orchestration выполняются вне Mobile App. Interstate, телефония и общая интеграция отдельного barcode-проекта — поздние этапы. Реальные SMS/OTP/email через отдельный модуль Twilio и физическая печать требуют подключения командой в согласованном scope; готовность этих интеграций не заявлена. Точные границы — [Release 1 decisions](requirements/RELEASE_1_DECISIONS.md).

## Первые действия команды

1. Открыть утверждённый прототип и прочитать scope вместе с FR/AC. Отделить ядро от Conditional, Deferred и служебных reference controls.
2. Разбить DP-01–10 на задачи mobile/backend/integrations/QA; указать FR/NFR, результат, зависимость и критерии проверки в каждой задаче. Оценки и исполнителей определяет команда.
3. Начать техническую основу и вертикальный сценарий «маршрут → Pickup → подписи/PDF → Dropoff/POD → синхронизация». Независимые задачи можно выполнять параллельно.
4. Получать доступы, проверять API/оборудование и выбирать средства реализации при выполнении соответствующих задач. Автор ТЗ не должен предварительно выполнять эти работы; отсутствие sandbox не останавливает подготовку пакета или независимые работы команды.
5. Проверять реализацию по AC и регистрировать возникающие вопросы в порядке ниже. Не выдавать тестовый адаптер или успешный unit test за готовую live интеграцию.

## Как решать вопросы при разработке

Наличие RQ/OQ не блокирует передачу этого задания. Уточнения обсуждаются с owner по мере работы над соответствующим участком, остальные задачи продолжаются. Рекомендуемые варианты — основа обсуждения, не автоматически утверждённые бизнес-решения.

| Вопрос | Когда уточнить | К кому / где основа |
|---|---|---|
| RQ-01: фиксация evidence между подписями | При реализации review/signing и изменения revision | Owner/Operations; варианты в Release 1 decisions |
| RQ-02: correction/void подписанного факта | При реализации исправлений и повторных подтверждений | Owner/Operations; исходный подписанный PDF всегда сохраняется |
| RQ-03: отмена/переназначение начатой точки | При реализации route updates/conflicts | Dispatch/Operations; не уничтожать уже записанный факт/evidence |
| RQ-04: допуск после Pre-trip Issue/смены машины | При реализации recovery vehicle cycle | Operations/fleet; комментарий об отсутствии данных не снимает route gate |
| API mapping, identity/session, файлы, ОС/принтер, численные NFR | При реализации соответствующей интеграции/модуля | Технические варианты готовит команда; бизнес-последствия согласует owner |
| Параметры пилота | При подготовке доступного пилота к приёмке/запуску | Owner/Operations/QA; BD-15 отложен |

Формат записи вопроса: ID RQ/OQ/INT или новый ID → связанная задача/FR → ситуация и влияние → рекомендуемый вариант → ответ owner → обновлённые документы/AC. Если правило уже согласовано, ссылаться на решение, а не согласовывать повторно. Редакционные уточнения не меняют scope; изменения бизнес-правил фиксируются в Decision Log.

## Версия и состав передачи

Пакет **v1.0** объединяет документы с собственными draft-версиями: draft обозначает открытые детали документа, а не отсутствие задания для команды. В составе сохранены 50 FR, 20 NFR, 140 AC, 18 UC и 10 этапов; статусы 55 Confirmed / 9 Needs Decision / 6 Proposed. Эти статусы не равны проценту готовности приложения.

[Манифест v1.0](current/DEVELOPMENT_PACKAGE_V1.0.json) перечисляет файлы пакета и SHA-256 их содержимого при передаче. Он фиксирует срез без commit/tag; после изменения файла соответствующий hash уже не совпадёт. Проверки и история ограничений сборки — [отчёт](current/RELEASE_1_DOCUMENTATION_CHECKS.md). Манифест не включает себя и изменяемый отчёт проверок.

При передаче копировать перечисленные файлы с сохранением путей и предоставить доступ к репозиторию/прототипу: ссылки на код/историю и пользовательское руководство используют структуру проекта. Локальные ignored DOCX/legacy evidence — вспомогательные материалы; перечислены в inventory и передаются отдельно, если потребуются команде. Они не являются скрытым условием начала работ по этому пакету.

## Как принимать работу команды

Результат каждой задачи — реализация, связанная с FR/AC, и проверка ожидаемых/ошибочных сценариев. Отдельно проверяются локальное и серверное сохранение, реальные файлы/PDF, повторные отправки, offline/restart и неподтверждённые операции. Для включённых каналов/устройств команда проводит реальные интеграционные проверки.

Реализованный продукт, подключённые интеграции и допуск пилота принимаются отдельно от документационного пакета. Поздние функции не объявляются выполненными; служебные prototype controls не превращаются автоматически в production administration.
