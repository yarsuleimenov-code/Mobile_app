## Цель и минимальный готовый результат

Пользователь — водитель. Нужен демонстрируемый сценарий: предрейсовый осмотр → работа по заказу → комментарий и подтверждение каждой стороны → связь с ответственными → послерейсовый осмотр.

Рекомендуемый scope: три задачи owner плюс согласованная на встрече внешняя навигация и дополнение инспекций приборной панелью/оборудованием. Всё — внутри существующего hi-fi прототипа, без нового приложения и реальных CRM, SMS, camera или Telegram API-интеграций. Внешние ссылки открываются реально; отправка сообщений не автоматизируется.

Готовый результат: доступные из штатного интерфейса экраны, сохранение сценария после обновления страницы, позитивные/негативные демонстрации, RU/EN инструкция и описание ограничений. В UI — обычные продуктовые названия, без mock/demo-пометок. Служебные сценарии — Administration.

## MOB — Послерейсовый осмотр

### Рекомендуемый сценарий

1. На Home после успешного Pre-trip появляется доступный `Post-trip inspection`. Просмотр предрейсового результата остаётся доступен.
2. Экран показывает тот же автомобиль и связанный цикл использования, checklist и фото. Открытие не зависит от того, загрузил ли водитель маршрут.
3. Пять обязательных фото: Front, Rear, Driver side, Passenger side, Dashboard. Dashboard нужен для фиксации приборной панели/индикаторов, не для автоматической оценки безопасности по фото.
4. Сохранить понятную структуру существующего checklist; добавить проверку корпоративных инструментов/оборудования. Начальный список для демонстрации — статический, с описанным допущением по филиалу.
5. `Issue` требует описания. Отдельное фото дефекта можно сделать необязательным дополнением; обязательные пять ракурсов сохраняются.
6. На Review водитель подтверждает достоверность записи. Завершённый результат: `Completed` либо `Completed — issues reported`, автомобиль отмечен `Needs attention` при дефекте.
7. Сохраняются автомобиль, ответы, фото-маркеры, дефекты и время. Итог доступен только для просмотра. При начале следующего цикла нужен новый Pre-trip; предыдущая пара осмотров сохраняется отдельно.

### Правила, предлагаемые для бизнес-валидации

- Дефект **не блокирует сдачу Post-trip**. Иначе водитель не сможет завершить именно тот отчёт, который сообщает о проблеме. Предрейсовый запрет отправления при Issue остаётся.
- Нельзя автоматически переносить post-trip дефект в новый цикл как исправленный. В прототипе показывать предупреждение при следующем Pre-trip; реальное разрешение эксплуатации и подтверждение ремонта — отдельный процесс.
- Незавершённые остановки не закрываются автоматически. Рекомендуется предупреждение с количеством оставшихся задач и явным подтверждением водителя перед завершением осмотра. Сам осмотр не изменяет статусы заказов.
- Под «закрытием рейса» в этой итерации понимается завершение цикла осмотров автомобиля. Authoritative route close и закрытие Interstate Trip — другие операции. Если требуется блокировать дальнейшие операции маршрута, это отдельное бизнес-правило для согласования.
- Не добавлять clock-in/clock-out, вычисление смены, зарплаты, ремонтные заявки или supervisor override.

### Приёмка

- Без ответа, любого обязательного фото или подтверждения завершение недоступно.
- Осмотр с Issue и описанием завершается; результат явно сообщает о дефекте.
- Пройденный Pre-trip нельзя использовать для следующего цикла после Post-trip.
- Обновление страницы сохраняет черновик и итог; данные Pre-trip не перезаписываются Post-trip.
- Непройденный Pre-trip продолжает блокировать загрузку маршрута.
- Складские Interstate-операции не получают новый vehicle gate.
- Текущие четыре фото и тексты Pre-trip обновляются до пяти в UI и инструкции одновременно.

## MOB — Комментарии каждой стороны при подтверждении

Реализовано локально: общий редактор на Review убран, каждая сторона комментирует на своём шаге. При OTP слова контакта записываются до проверки кода. [Правила и проверки](HANDOFF_COMMENTS_SIGNING_WIREFRAME.md). Поля contact/driver сохраняются в конкретной версии документа.

### Рекомендуемое изменение

- Убрать общий редактируемый `Comments from both parties` из Review.
- На шаге контактного лица, непосредственно перед подписью, добавить необязательный `Your comment`. После принятия подписи этот комментарий не редактируется на шаге водителя.
- На шаге водителя, перед его подписью, добавить отдельный необязательный `Your comment`. Комментарий контакта здесь только для чтения.
- Применить одинаковую логику к Pickup, Supplemental Pickup и Delivery.
- В готовом eBOL/POD оставить оба комментария с обозначением стороны. Комментарии принадлежат только подписываемой версии; уже подписанные документы не меняются.
- Повреждение/несогласие по-прежнему оформляются как Exceptions. Свободный комментарий не заменяет обязательную фиксацию исключения.

### OTP: явное допущение

При OTP контакт не подписывает экран. Простое решение: ввод Contact comment внутри контактного OTP-подтверждения **до проверки кода**, затем только просмотр; Driver comment — на экране подписи водителя. Не создавать фиктивную клиентскую подпись. Если слова клиента записывает водитель, не представлять их как самостоятельно введённый клиентом текст.

Изменение содержимого, относящегося к подтверждению контакта, после успешного OTP требует повторного подтверждения. Обычный будущий комментарий водителя не отменяет OTP. Точные границы замораживаемых полей проверить при реализации, сохранив существующие правила доказательств.

### Приёмка

- Стороны последовательно видят собственное поле; пустой комментарий допустим.
- Back/refresh сохраняют черновики без подмены стороны и версии.
- Принятая контактная подпись не остаётся действующей после изменения её подтверждаемого текста; при возврате и редактировании нужна повторная подпись.
- Locked Pickup/Delivery/Supplemental не допускают изменения комментариев.
- Оба способа подтверждения остаются рабочими. В OTP сохраняется текущая демонстрационная логика: шесть цифр, любой код кроме `111111`; подпись водителя обязательна.

## MOB — Внутренние контакты заказа

### Рекомендуемый сценарий

- В Order details разместить компактную карточку `Team contacts`.
- Реализовано локально: [Team contacts — правила, ограничения и проверки](TEAM_CONTACTS_WIREFRAME.md).
- Три строки: Dispatcher, Broker, Manager; в каждой — имя и кликабельный `@nickname`.
- Ссылка открывает `https://t.me/<nickname>`; приложение или web-страница Telegram выбираются устройством. Не гарантировать открытие установленного приложения из desktop браузера.
- Контакты определяются заказом, а не общим списком филиала. Использовать статические данные хотя бы для двух заказов с разными диспетчерами.
- Из Pickup/Dropoff обеспечить понятный переход к контактам текущего заказа. Номер заказа виден рядом; рекомендуется простое `Copy order number` для передачи собеседнику.
- При отсутствующей роли показать `Not assigned`, без подстановки произвольного сотрудника. Не добавлять CEO.
- Рабочие часы обсуждались, но конкретные данные не определены: оставить вторым шагом. Не показывать выдуманный online-статус.

### Приёмка

- Смена заказа меняет его ответственных; данные не смешиваются с customer contact.
- @nickname ведёт на соответствующую Telegram-ссылку; сообщение самостоятельно не отправляется.
- Отсутствующий контакт не создаёт пустую/сломавшуюся ссылку.
- Демонстрационные аккаунты не выдаются за подтверждённые аккаунты сотрудников; реальные адресаты согласуются перед внешним показом.

## Дополнительные задачи встречи

### Внешняя навигация — включить в ближайшую итерацию

Реализовано локально: [сценарии, ограничения и проверки](EXTERNAL_NAVIGATION_WIREFRAME.md). Выбор навигатора, ETA и собственная карта не входят в scope.

Действие `Navigate` у адреса конкретной Pickup/Dropoff остановки. Открывает карту с адресом назначения. Не строим собственный навигатор и не подключаем платный routing API. В web-прототипе — универсальная ссылка на карты; гарантированный выбор навигатора по умолчанию на телефоне относится к будущему mobile client.

Проверки: разные адреса Pickup/Dropoff одного заказа, корректная передача специальных символов, отсутствующий адрес без активной ссылки. Нельзя брать первый task заказа вместо текущей остановки.

### Requirements — отдельная смежная задача

На встрече приняли в работу выделенные требования к обработке: распечатать BOL, подготовить упаковку и т. п. Это не комментарии сторон в подписанном документе и не просто часы доступа к адресу.

Рекомендуемый минимум: одно необязательное текстовое `Requirements` на заказ, заметно отображаемое в Order details и операционном контексте. Если текст относится только к Pickup, это явно указывается в тексте. Отдельные Pickup/Delivery comments сохраняются. Не добавлять новый справочник требований.

Перед реализацией mapping требуется проверить, какое CRM-поле действительно можно переиспользовать (general/broker comment) и свободно ли предлагаемое Spoke custom property. На встрече эти технические варианты обсуждали, но действующая конфигурация не проверена. В прототипе уже есть `Special Cargo` category/details: не уничтожать их переименованием без решения о совместимости.

Мобильная визуализация после согласования может быть отдельной небольшой задачей. Kommo → DeliveryPickupTable → Spoke pipeline находится вне этой итерации мобильного репозитория.

### Склад — сначала описание сценария

В прототипе уже есть базовые Interstate loading/unloading и BOL. Дельта встречи — складская приёмка, отправка, аудит, фиксация расхождений и внутреннее взаимодействие. Сначала определить пользователя, единицу учёта, исходный manifest, действия при недостаче/повреждении и кто подтверждает результат. Не начинать новый складской модуль под видом небольшого расширения осмотра.

### Вне мобильного scope

Обсуждались FirstDibs в CRM, очистка DeliveryTable/воронок, подсказки Kommo, DailyMetrics/BI и Xeon, тарифный калькулятор и зоны, сервис отзывов, разделение BOL по получателям, будущая оценка груза по фото, фиксированная дата доставки и платежи. Это смежный контекст, не основания добавлять все эти функции в текущий wireframe. FirstDibs и звонки из заказа не возвращаются в новый mobile backlog.

## План принятия в работу и реализации

1. **Согласование scope.** Подтвердить три основных задачи и включение навигации/dashboard/equipment. Правила Post-trip, незавершённых остановок и OTP-комментария выше — рекомендации, не дословные решения встречи. Общий список вопросов не нужен; корректировки этих допущений достаточно.
2. **Комментарии.** Сохранить существующую модель eBOL; перенести редакторы, защитить принятые подтверждения от последующих изменений, проверить все версии и оба метода.
3. **Контакты и навигация.** Статические связи order → team, компактная карточка, переходы из операций, ссылки и номер заказа. Адрес выбирать по stop, контакты — по order.
4. **Инспекции.** Дополнить Pre-trip, добавить Post-trip и минимальный локальный цикл использования автомобиля. Переиспользовать визуальные элементы; не копировать предрейсовое правило запрета завершения при Issue.
5. **Документация и проверка.** Обновить спецификации инспекций/eBOL, CURRENT_STATE, RU/EN пользовательские инструкции и сценарий owner-demo. Будущие предложения не описывать как работающие функции.
6. **Приёмка и публикация.** Показать позитивный и негативный сценарии; зафиксировать замечания owner. Commit/push — после соответствующего разрешения. Этот документ сам по себе не является приёмкой реализации.

Необходимые проверки реализации: domain tests на инспекции и неизменяемость версий, штатные test/build проверки проекта, браузерный прогон на мобильной ширине 390 px и desktop preview, Back/refresh, ошибка локального сохранения, два разных заказа, подпись и OTP, дефект в Post-trip и следующий Pre-trip.

Маршрут демонстрации: Pre-trip с пятью фото → заказ и Navigate → контакты заказа → Pickup/Delivery с отдельными комментариями и подписью → другой заказ через OTP → Post-trip с дефектом → просмотр итога → новый цикл требует Pre-trip. Для навигации и Telegram отдельно проверяются реальные внешние ссылки без отправки сообщений.

Риски: настоящий camera/media storage и серверный аудит отсутствуют; localStorage не обеспечивает production надёжность; маршрут и цикл автомобиля пока не имеют authoritative backend; ссылки Telegram могут вести на реальные чужие аккаунты; фото приборной панели не доказывает исправность машины. Нормативную или юридическую готовность этим планом не утверждаем.
