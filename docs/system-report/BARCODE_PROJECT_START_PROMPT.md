## Задание агенту

Работай как Senior Business Analyst, Product Manager и Product Engineer. Создай отдельное iOS-first приложение для учета, маркировки и сканирования грузовых мест в заказах Zaberman: складские сотрудники используют устройства Apple. Сначала проверь реализуемость Bluetooth-печати на iPhone/iPad, затем разработай минимальный работающий прототип с Google Sheets и Apps Script. В дальнейшем продукт должен переноситься в мобильное приложение Zaberman как модуль.

Предпочитай общий код интерфейса и бизнес-логики для iOS и Android, если это не мешает надежной Bluetooth-печати и offline-работе. Google Sheets и Apps Script — общий backend. Подключение принтера и сканирование реализуй через подходящие платформенные компоненты; одинаковый интерфейс не означает одинаковую аппаратную интеграцию. Поддержку Android добавляй после подтверждения основного iOS-сценария. Не выбирай технологию до проверки совместимости конкретного iPhone/iPad, версии iOS/iPadOS, SDK и модели принтера. Общего заявления производителя «поддерживает iOS» недостаточно.

Не изменяй существующий проект Mobile_app. Если в новом проекте отсутствует AGENTS.md, создай его, README и минимальную документацию источников, схемы данных, API и проверок. Предпочитай простое решение; не начинай с ERP, маршрутизации, BOL, POD или сложной системы ролей.

## 2. Ключ заказа и формат кода места

Последнее указание owner имеет приоритет над прежним промптом и Stage 0 в части barcode payload: **код должен содержать ID заказа и номер конкретного места, как в работающем интерфейсе прототипа**.

Предложенный контракт нового продукта:

`ZB-<External ID>-<PlaceNo>`

Пример на условном заказе: External ID `12345678`, место 1 → `ZB-12345678-01`, место 2 → `ZB-12345678-02`.

- Каждый физический CargoPlace получает отдельный код.
- PlaceNo — положительный, монотонно выдаваемый номер внутри заказа; минимум две цифры на этикетке, без ограничения в 99 мест.
- Код после выдачи не меняется; номера удаленных/аннулированных мест не используются повторно.
- Reprint сохраняет код и PlaceID, фиксируя автора, время и причину.
- Не включай текущее число мест N, статус, размеры, адрес или TripID в идентификатор.
- `n/N` на этикетке — отображаемая информация, а не часть уникального кода.
- Не удаляй нецифровые символы External ID автоматически. Проверь допустимые значения и правила разбора кода; при необходимости используй однозначное обратимое кодирование сегмента ID.
- В прототипе используется Code 128. Для нового продукта сравни Code 128 и QR с одним и тем же payload; выбери основной формат после теста оборудования. Требование «ID + место» относится к содержимому кода, а не предписывает символогию.

Внутренний immutable `place_id` UUIDv7 можно сохранить для offline создания и последующего переноса в Zaberman. Храни отдельно `place_id`, `external_order_id`, `place_no` и `barcode_value`. UUID не заменяет требуемое содержимое кода.

**Критический риск offline:** два телефона не должны выдать одинаковый PlaceNo одного заказа. Перед реализацией выбери простую безопасную политику: один ответственный creator на заказ или заранее зарезервированные диапазоны номеров. При отсутствии резерва нельзя печатать потенциально конфликтующий окончательный код. Не менять напечатанный код после sync. Одного UUID недостаточно для уникальности `External ID + PlaceNo`.

External ID может повторяться в строках Pickup/Dropoff. Это не обязательно дубликаты заказов. Разделяй Order и Operation/Task; не выбирай молча первую/последнюю строку и не смешивай адреса разных операций. Номер строки и название лида не являются устойчивыми ключами. Если один External ID относится к разным заказам, выдели конфликт для разбора вместо склейки.

Проверь External ID совместно по CA и NY. Один заказ может участвовать в операциях обоих филиалов: источник строки не должен автоматически создавать второй Order или новые CargoPlace. В то же время одинаковый External ID разных заказов нельзя молча объединять. До подтверждения глобальной уникальности раздельно храни происхождение строк и показывай конфликт. Нумерация мест ведется по каноническому заказу, не начинается заново при переходе между филиалами. Если IDs уникальны только внутри филиала, согласуй namespace кода до печати, поскольку `External ID + PlaceNo` иначе не обеспечивает уникальность в общем приложении.

| Package count | Плановое число мест; фактические CargoPlace создаются отдельно |
| Weight (lb) | Исходный вес с единицей lb; не распределять автоматически между местами |

| Pickup due date / Delivery due date / Last change date | План/время изменения источника; не подменять временем сканирования |

В Orders/Operations сохраняй происхождение: spreadsheet ID, sheetId, source_branch (`CA`/`NY`), External ID, время импорта и при наличии source modified time. Заказ может иметь несколько исходных ссылок/операций; не перезаписывай одну ссылку другой при импорте второго филиала. Повторный импорт обновляет проекцию плановых данных, не перезаписывая фактические места, barcode, события и подтвержденные операции.

Зафиксировано на 14 октября: timezone S1 — Europe/Moscow, S2 — Etc/GMT. Это настройки таблиц, не подтверждение бизнес-timezone. Храни события в UTC, сохраняй исходную интерпретацию плановых дат; согласуй рабочую timezone до полевого запуска.

## 4. Scope разработки и минимальная схема

Предложи минимальные листы `Orders`, `Operations`, `CargoPlaces`, `Events`, `Trips`, `Manifest`, `LabelPrints` и служебную configuration при необходимости. Не создавай отдельный лист на каждый заказ. Контакты и авторизацию реализуй минимально достаточным способом.

Основные сценарии:

1. Менеджер импортирует выбранные заказы из CA и NY в общий backend, фильтрует по филиалу и находит заказ по External ID. Если ID неоднозначен, приложение показывает варианты и происхождение вместо автоматического выбора.
2. Сотрудник создает каждое физическое место, получает номер, код и label.
3. Печатает по Bluetooth непосредственно со смартфона и выполняет scan-test.
4. Сканирует при Pickup, Receiving, Loading, Unloading и Dropoff.
5. Lookup только показывает карточку; операция отдельно проверяется и подтверждается.
6. Loading проверяет выбранный Trip/Manifest; Unloading — фактически loaded set; Dropoff — ожидаемый комплект.
7. Неизвестный код, duplicate, missing, extra, wrong Trip и damage обрабатываются явно.
8. Offline-события сохраняются локально и синхронизируются с pending/failed/conflict состояниями.

Минимальный Event: event_id, place_id, barcode_value, external_order_id, operation_id/type, TripID при применимости, from/to Location, occurred_at, received_at, actor_id, device_id, result, reason.

Повторный event_id не создает повторную операцию. События и текущее состояние сохраняются отдельно. Защити конкурентные записи Apps Script и документируй восстановление после частичной записи; не предполагай транзакционность Sheets.

Последовательность: исследование оборудования → bench-test Bluetooth-печати на реальном iPhone/iPad сотрудников → управляемый импорт → Order/CargoPlace/Print/Scan/Event → offline/idempotency → Manifest checks → полевой пилот на iOS. При отсутствии устройства продолжай независимую разработку, но не объявляй Bluetooth-печать проверенной. Android не заменяет приемочную проверку на Apple.

## 5. Что необходимо уточнить

Для начала исследования источников достаточно. Следующие решения нужны для соответствующих этапов, а не являются причиной остановить весь проект:

- **Источник импорта:** CA и NY включены в первоначальный scope. Подтверди глобальную уникальность External ID и правило общего заказа между филиалами. Data не добавлять как третий источник без проверки пересечений с CA/NY.
- **Примеры:** выбрать в S1 несколько записей с одним External ID на Pickup/Dropoff и несколько заказов с несколькими местами. Нужны фактические значения Type и правило названия лида.
- **Номера мест:** подтвердить одного creator на Order в MVP либо резервирование PlaceNo для нескольких offline устройств.
- **Оборудование:** используемые iPhone/iPad и версии iOS/iPadOS, точная модель/SKU Bluetooth-принтера, размер/тип этикеток и доступность устройств для теста. Подтверди наличие подходящего iOS SDK и условия выпуска приложения с его Bluetooth-интеграцией.
- **Deployment:** кто владеет Apps Script, под какой учетной записью он исполняется, кто имеет доступ к S1/S2 и как сотрудники авторизуются.
- **Interstate:** источник существующих TripID/Manifest; если его нет, реализовать ручное создание в S2 как явное временное решение.
- **Операции:** минимальный перечень статусов/Location, кто подтверждает расхождения и частичное выполнение; исходные lead statuses не считать их заменой.
- **Границы нагрузки:** число мест/день, пользователей и срок хранения истории, рабочая timezone.
- **Новый workspace:** путь отдельного проекта. Не создавать его внутри исходного приложения без явного указания.

Не запрашивай пароль или секреты в чате; используй штатную настройку доступов и deployment.

## 6. Критерии готовности первого работающего среза

- Заказ найден по External ID после импорта из S1 в S2.
- Заказы CA и NY доступны в одном приложении с фильтром филиала; повторный импорт не создает дубликаты. Один межфилиальный заказ сохраняет PlaceID, коды и историю при переходе между складами; коллизии External ID не объединяются молча.
- Два места одного заказа имеют разные номера и коды в формате ID + место.
- Код сохраняется после refresh, reprint, повторного импорта и sync.
- Реальный iPhone/iPad сотрудников создает label offline и печатает по Bluetooth без PC и интернета; физический тест записан с моделями устройств, версиями OS, SDK и способом подключения.
- Scan открывает правильное место; неизвестный код не создает запись.
- Операция сохраняется в S2 с исходным временем, пользователем и устройством.
- Повторные scan/send не дублируют факт; offline restart не теряет очередь.
- Политика выдачи PlaceNo не допускает одинаковых напечатанных кодов с двух телефонов.
- Оригинальный workbook S1 не изменен.

Результат: исходный код, Apps Script, schema/mapping, инструкции import/deploy/build, журнал проверок и ограничения. В README нового проекта зарегистрируй S1–S4 с ролями и правами. Каждое расхождение с документацией старого приложения фиксируй как осознанное решение нового продукта.
